# Development

This page is for contributors. To use plain, start with [getting started](getting-started.mdx).
[CLAUDE.md](../CLAUDE.md) gives coding agents a short overview, the daily commands, the rules for all tasks and the
file to read for each task. [CODING_STANDARDS.md](../CODING_STANDARDS.md) contains the rules for code and tests,
and a map of the source folders.

## Build and test

```sh
npm ci
npx playwright install chromium
npm run build    # compile src/ to dist/, remove stale output and write the generated plugin files again
npm test         # build, then run the tests in dist/**/*.test.js and scripts/*.test.mjs
npm run check:docs
npm run check:agent-notes
npm run test:mods  # the session pane mod tests (claude plugin test). Needs the claude CLI. Not in npm test
npm run verify   # the key-free gate: tests, docs, examples, package and plugin install
```

`npm run verify` runs `npm test`, `npm run check:docs`, `npm run check:agent-notes`, `npm run check:examples` and
`npm run test:plugins`. The CI workflow runs the same command.

`npm run check:examples` validates the specs in `examples/`, `examples/mobile/` and `e2e/`. It also validates
each full spec and config example in the user docs, with the CLI of its engine.

`npm run check:docs` checks the user docs: README.md, `docs/*.mdx` and `examples/mobile/README.md`. Each file must
compile as MDX and show correctly on GitHub. The text must follow the ASD-STE100 rules that a script can test, for
example a maximum of 25 words in a sentence. All relative links and anchors must resolve. The CI workflow runs the
same check. The full writing rules are in `.claude/skills/writing-docs/SKILL.md`.

`npm run check:agent-notes` checks the agent notes: `CLAUDE.md`, `CODING_STANDARDS.md`, each `CLAUDE.md` below the
root and the skills in `.claude/skills/`. A file must not have more lines than its limit. Each path, cited section
and named symbol in the files must exist. The full rules for these files are in
`.claude/skills/writing-agent-notes/SKILL.md`.

`npm test` needs no API key and no native SDK. It runs these tests:

- The browser runner against headless Chromium, with `data:` URLs.
- The desktop and mobile sessions, with injected adapters and injected Jev decisions.
- Mobile requests from real WebdriverIO to a local Appium-protocol fixture, for Android and iOS.
- MCP recording and replay of the saved specs.
- The pre-PR hook, in a temporary repository with a git worktree.

The session pane mod in `mods/session-pane/` has its own tests. `npm run test:mods` runs them with
`claude plugin test`. If Anthropic disables installed mods for your account, the command prints a notice and
returns exit code 0, but no test runs. The build copies the mod into each plugin, without the tests.

These tests do not prove that a real device, simulator or desktop works. For that, use the
[native smoke tests](#verification).

## Validation before a pull request

Before you open a pull request, run the full validation loop:

```sh
node scripts/validate.mjs
```

The script stops at the first failure. In order, it runs:

1. `npm run verify`.
2. The live e2e suite, `node scripts/e2e.mjs`.
3. The claims gate, `node scripts/benchmark-claims.mjs --gate`. A false pass or a Jev error fails it.
4. The agent evals, `node scripts/eval-agent.mjs`, when the MCP tools, their results or the browser skill
   changed.
5. The routing evals, `node scripts/eval-routing.mjs`, when an agent note changed.

At the end, it lists the benchmarks that the changed files need. Compare each one with a run on main. The
`validating-changes` skill in `.claude/skills/` gives the full procedure, also for the review of the code and
the docs. Codex reads the same skill from `.agents/skills/`.

A hook in `.claude/settings.json` and `.codex/hooks.json` stops `gh pr create`. It lets the command run only
when `scripts/validate.mjs` passed on the same files as HEAD. The hook checks the checkout where the command
runs, also in a git worktree.

### Live e2e suite

The live checks need a Jev key and a build. They use no remote site. `e2e/site.mjs` serves all the pages on
`127.0.0.1` from the process of the runner. Thus a failure comes from plain or Jev, not from the network. The specs
get the address of the site from `${env.site}`.

- Each `e2e/*.yaml` spec must pass. A spec with the tag `expect-fail` must end `fail`. A pass there is a false
  pass.
- A spec that passes only on a retry counts, but the runner lists it as flaky.
- The runner also records a login through the MCP server and runs the saved spec again.

To run one spec, use `node scripts/e2e.mjs --only forms`. To run the specs without the MCP check, add
`--skip-mcp`. `npm run verify:live` builds, then runs the e2e suite and the claims gate.

The totals of Jev calls and tokens include all attempts. With the default `--retries 1`, each spec that does not
pass runs two times, also each `expect-fail` spec. To measure the Jev cost of a change, use `--retries 0`.

### Browser exploration

Run measured MCP flows against disposable local sites with a Jev key:

```sh
node scripts/autoresearch-web.mjs --runs 3 --out /tmp/research.json
```

The report records each call, its elapsed time, Jev tokens and independent DOM checks.
The flows cover login, forms, frames, editors, inert backgrounds and disabled fieldsets.
An unexpected result makes the command fail.
Use `--cli /path/to/dist/cli.js` for a baseline build.
Use `--observe` to record findings without a failed exit status.

### Agent evals

`node scripts/eval-agent.mjs` gives tasks on the local site to a real `claude -p` agent and a real `codex exec`
agent. It grades each run:

- The final answer must contain the text that the page shows.
- The agent must reach the page only through the plain tools, with no failed tool call.
- The number of tool calls must stay in the budget of the task.
- A spec that the agent saves must pass when the CLI runs it.

Each agent runs isolated from your own setup, with the skill and the MCP server of the checkout. Codex gets an empty
`HOME`, so it does not read your own skills in `~/.agents/skills`. The plain MCP server keeps your `HOME`, so it
finds `~/.config/plain/.env` and the Playwright browsers. The evals cost Claude and Codex usage. CI does not run
them. Use `--agent claude` or `--only login` to run fewer.

If a run fails, the eval prints the folder with the transcripts of the failed runs. A task can fail now and then
with no change in plain. To find out if your change is the cause, compare main and your branch:

1. Run the same task on main and on your branch at the same time, for example with `--only reference --runs 10`.
   The failure rate of a task changes from hour to hour.
2. Use the same environment for the two runs. `claude -p` gets the environment of the process that starts it,
   also the `CLAUDE_CODE_*` variables of a Claude Code session.

### Routing evals

`CLAUDE.md` is short: for most rules, it sends the agent to another file. `node scripts/eval-routing.mjs` checks
that a new agent still finds these rules. It asks each question in `scripts/routing-cases.json` to a real
`claude -p` agent and a real `codex exec` agent, with read-only tools. The answer must match all the `expect`
patterns of the case and none of its `forbid` patterns.

Each agent runs isolated from your own setup, with the instruction files of the checkout. Settings that your
organization manages still apply. The evals cost Claude and Codex usage. CI does not run them. If you change a route or a rule that an agent must find, add or change a
case.

### Continuous integration

- The `Test` workflow runs `npm run verify` on each pull request and on main. It then checks that the generated
  plugin files match the build.
- The `Live` workflow runs the e2e suite and the claims gate. It starts on each pull request, because main
  requires its `live` check. If the pull request does not change the runtime, the e2e suite or the eval data, the
  check passes and the workflow runs nothing more. The `RUNTIME` pattern in `.github/workflows/live.yml` lists
  these files. The workflow needs the `TYPESAFE_API_KEY` repository secret. Without it, the workflow fails, but on
  a pull request from a fork it is skipped.
- The `Publish` workflow publishes the npm package. Refer to [releases](#releases).

To run one test file or one test case after a build:

```sh
node --test dist/browser/runner.test.js
node --test --test-name-pattern "<name>" dist/jev/pick.test.js
```

## Build output

The repository does not contain `dist/`. Run `npm run build` after a clone and after each change in `src/`.
After it compiles, the build removes each file in `dist/` whose source in `src/` is gone. Thus the compiled test
of a deleted source file does not run again.
Then the launchers in `bin/` run the checkout, for example `node bin/plain.mjs examples/todo.yaml`.

`npm run build` also writes the generated plugin files: the MCP configs, the npx shim, the plugin versions, the
version in the `npx` commands of the skills, the license and the session pane mod. Do not edit these files by hand. Commit them
with the change. The `Test` workflow fails if they are different from the build output.

## Releases

The npm package `@gabe4coding/plain` contains `bin/`, the compiled `dist/` without tests, and the root lockfile as
`npm-shrinkwrap.json`. Thus an install from npm uses the locked dependency graph. `npm pack` and `npm publish`
compile a clean `dist/` first. The package name has a scope, because the name `plain` without a scope belongs to
a different npm package.

To release a version:

1. In a pull request, run `npm version <version> --no-git-tag-version`. It changes `package.json` and
   `package-lock.json`.
2. Run `npm run build`. The build writes the new version into the three plugins.
3. Merge the pull request.

Use semantic versioning. A change that removes or renames something users write or call needs a new major
version. Examples are a CLI flag, a config key, a spec key, a step kind, an Action input and an MCP tool. The
build also writes the version into the browser skill, so `scripts/validate.mjs` runs the agent evals for a
version change.

On each push to main, the `Publish` workflow compares the `package.json` version with npm. If npm does not have
this version, the workflow runs `npm run verify`, publishes the package with provenance and pushes the tag
`v<version>`. A version that is already on npm is not published again.

Then the workflow installs the published version from npm. The registry can serve the old version list for up to
5 minutes after a publish. Thus the workflow tries the install again with longer delays, for up to 10 minutes. It
fails if the install does not work in that time. It also fails if a direct dependency does not have its lockfile
version, because then npm did not use the shrinkwrap. Then it runs the CLI once.

The plugins run `npx -y --package=@gabe4coding/plain@<version>`. Thus a merged version bump starts to work in the plugins
when the `Publish` workflow is complete.

The workflow uses npm trusted publishing. The first publish needs the `NPM_TOKEN` repository secret, because
npm sets a trusted publisher only on a package that exists:

1. Create a granular npm access token with write access. If your npm account uses two-factor authentication,
   select the option that lets the token bypass it.
2. Add the token as the `NPM_TOKEN` repository secret.
3. Let the `Publish` workflow publish the first version.
4. On npmjs.com, add a trusted publisher for the package: GitHub Actions, this repository, workflow `publish.yml`.
5. Remove the `NPM_TOKEN` secret, and delete the token on npmjs.com.

## Repository layout

```text
package.json                 all dependencies, the three CLI binaries, build and test scripts
src/                         browser, desktop, mobile and shared code, most tests next to their module
bin/                         CLI launchers, the bin entries of the npm package
plugins/
  plain/               browser plugin: manifests, MCP config, skill
  plain-computer/      desktop plugin
  plain-mobile/        mobile plugin
scripts/                     plugin build, smoke tests, benchmarks, evals, the validation loop
  *-states/                  saved pages for the Jev benchmarks: large one-line JSON, leave out of repo-wide searches
e2e/                         the live e2e suite: its local site and specs
examples/                    browser specs against public demo sites; examples/mobile/ for mobile
docs/                        user documentation; docs/benchmarks/ for benchmark reports
```

## Plugin packaging

One root `package.json` and one `package-lock.json` own the dependencies of all engines. Do not add a package
manifest, a lockfile, a symlink or a parent-directory import to a plugin.

Each plugin directory contains:

- The portable manifests `plugin.json` and `mcp.json`.
- The Claude Code manifests `.claude-plugin/plugin.json` and `.mcp.json`. The server runs `${CLAUDE_PLUGIN_ROOT}/bin/npx.mjs`.
- The Codex manifest `.codex-plugin/plugin.json`. It uses the same `.mcp.json` and `skills/`.
- The skill in `skills/`.
- The generated `bin/npx.mjs`, `LICENSE` and session pane mod in `hooks/`.

The MCP configs run `node bin/npx.mjs -y --package=@gabe4coding/plain@<version> <cli> ...`. `<version>` is the
`package.json` version, and the plugin version is the same. `bin/npx.mjs` is a copy of `scripts/plugin-npx.mjs`.
It starts `npx` with the MCP channel as its input and output. On Windows, it starts `npx` through `cmd /c`,
because some plugin hosts cannot start `npx` directly. In a checkout of this repository, `npx` uses the checkout as
the installed package and does not find the CLI. Thus in a checkout, the shim requests the package through an npm
alias: `gabe4coding-plain@npm:@gabe4coding/plain@<version>`. Then `npx` installs the package in its cache, and the CLI
runs in the same folder. A plugin host updates a cached plugin only when its
version changes. Thus each new package version is also a new plugin version.

Keep the `name` and `description` equal in the three `plugin.json` files of each plugin. The build writes the
`version`. Both root marketplaces, `.claude-plugin/marketplace.json` and `.agents/plugins/marketplace.json`, list
the three plugin directories.

To check the plugins as a plugin host sees them, run:

```sh
npm run test:plugins
```

This script packs the npm package with `npm pack` and checks its file list. Then it copies each plugin to a
temporary folder and compares the three manifests and the MCP configs. It starts each MCP server with the `npx`
command of its config and lists the MCP tools. The command uses the packed file in place of the npm version. It needs no API
key, but it needs the npm registry for the dependencies.

Pitfalls:

- Keep `.env` files out of the plugin directories. Codex copies the plugin directory into
  `~/.codex/plugins/cache/`.
- A plugin from a clone runs the npm version in its MCP config, not the code of the clone. To try a change in the
  code with an agent, register the server of the checkout, for example
  `claude mcp add plain-dev -- node /absolute/path/to/plain/bin/plain.mjs --headless mcp`.
- To try a change in a skill or the session pane mod, run
  `claude --plugin-dir /absolute/path/to/plain/plugins/plain`. Use the same command for
  `plugins/plain-computer` and `plugins/plain-mobile`.
- `AGENTS.md` is a symlink to `CLAUDE.md`. Codex reads the same repository guidance as Claude Code.

## Verification

The native smoke tests are opt-in. They run on a real desktop, device or simulator. Each test builds the project
first.

### Desktop on macOS

```sh
npm run test:computer:mac
```

The test compiles a disposable Cocoa application with `xcrun clang`, then removes it. Give the host that runs Node
the Accessibility and Screen Recording permissions. Without Screen Recording, add `-- --skip-screenshot`.

The test injects deterministic Jev decisions and needs no API key. It checks the real application state after
attach, tree capture, fill, click, check and uncheck, a key press, hover and a PNG screenshot. A second `check` on
a checked box must not change it. A fill in the secure Password field must be found as secure and must not show
in the tree.
Windows and Linux need the same kind of run on their own hosts before you claim native parity.

### Mobile connection

This test connects to your installed test app, reads the tree and takes a PNG screenshot. It needs no API key.

```sh
PLAIN_MOBILE_PLATFORM=android \
PLAIN_MOBILE_DEVICE=emulator-5554 \
PLAIN_MOBILE_APP=com.example.fixture \
npm run test:mobile
```

| Variable | Meaning |
|---|---|
| `PLAIN_MOBILE_PLATFORM` | `android` or `ios`. |
| `PLAIN_MOBILE_DEVICE` | Device ID: ADB serial or UDID. |
| `PLAIN_MOBILE_APP` | App package or bundle ID. |
| `PLAIN_MOBILE_CAPABILITIES` | Optional. A JSON object of extra Appium capabilities. |
| `PLAIN_APPIUM_URL` | Optional. The Appium server. Default `http://127.0.0.1:4723`. |

This test does not check taps, input or gestures.

### Android fixture

This test builds a small offline Android app, installs it, and does real text entry, check and uncheck, tap, long
press, scroll, swipe and screenshots. It records a flow through MCP, restarts the app and runs the saved spec. Then
it removes the app. The saved spec must have `${env.password}` for the Password field, and the replay reads the
value from `$PASSWORD`. If the fixture app is already installed, the test stops and does not replace it.

Prepare the host:

1. Install Android SDK Platform 36 and Build-Tools 36.0.0.
2. Set `ANDROID_HOME` (or `ANDROID_SDK_ROOT`) and `JAVA_HOME`.
3. Make sure that `zip` is on your `PATH`.
4. Start your emulator.
5. Start Appium with the UiAutomator2 driver.

You do not need Gradle or an application project.

```sh
PLAIN_MOBILE_DEVICE=emulator-5554 npm run test:mobile:android
PLAIN_MOBILE_DEVICE=emulator-5554 npm run test:mobile:android -- --live-jev
```

- The default run injects deterministic decisions. `--live-jev` uses real Jev picks and judgments, with your key
  from the repository `.env` or the user env file.
- At the end, the test prints a temporary folder with `recorded.yaml`, `report.json` and `preview.png`.
- To use a different installed Build-Tools version, set `PLAIN_ANDROID_BUILD_TOOLS`.

This test checks native Android controls. It does not prove React Native or iOS parity.

### iOS Simulator fixture

This test builds an offline UIKit app with the Xcode simulator SDK and installs it. It records native actions
through MCP, restarts the app and runs the saved spec. Then it removes the app. As on Android, the Password field
must be saved as `${env.password}`. If the fixture app is already installed, the test stops. You do not need an Apple developer account.

Prepare the host:

1. Install Xcode and an iOS Simulator runtime, iOS 16 or newer.
2. Complete the first-launch setup of Xcode. Make sure that `xcode-select -p` shows a path in Xcode.
3. Install the Appium XCUITest driver before you start the Appium server.
4. Boot an iPhone simulator.

```sh
xcrun simctl list devices booted
PLAIN_MOBILE_DEVICE=<simulator-udid> npm run test:mobile:ios
PLAIN_MOBILE_DEVICE=<simulator-udid> npm run test:mobile:ios -- --live-jev
```

- The first session builds WebDriverAgent. This can take some minutes. The test allows 4 minutes for each Appium
  request.
- Set `PLAIN_APPIUM_URL` if your server uses a different address or port.
- At the end, the test prints a temporary folder with `recorded.yaml`, `report.json` and `preview.png`.
- The fixture closes its keyboard with its Done key. A generic `press: HideKeyboard` can fail on iPhone.

A pass on the simulator does not prove physical iPhone or React Native parity.

## Performance checks

Build first. Most benchmarks ask Jev about saved pages or saved cases: they need an API key, but no site.
`benchmark-mcp.mjs`, and `benchmark-steps.mjs` without `--e2e`, also need the public demo sites, so a site problem
can fail a run. `benchmark-locators.mjs` needs no API key. `benchmark-snapshots.mjs` needs one only with `--live-jev`.

To compare a change against a saved run, run `benchmark-steps.mjs` with `--e2e`:

```sh
node scripts/benchmark-steps.mjs --e2e --mode judge --runs 3 --out /tmp/new.json --compare /tmp/base.json
node scripts/benchmark-mcp.mjs --cli dist/cli.js --gap 5000 --runs 2
```

`benchmark-steps.mjs` reports the step overhead for each phase: the step time minus the page action time.
`benchmark-mcp.mjs` times an agent-style MCP session, with think time between calls.

With `--e2e`, `benchmark-steps.mjs` runs the specs of `e2e/` on the local site in `e2e/site.mjs`. A slow or failed
step is then the result of plain or Jev, not of the network.

- The specs with the `expect-fail` tag do not run. They fail on purpose, so their time is not step overhead.
- To run only some specs, give their files, for example `e2e/login.yaml`.
- Each run starts from a new copy of `e2e/` in a temporary folder. The lock files do not go into the repository.
- In `no-judge` and `auto-healing` mode (the default), one judge run first writes the lock files that each run
  replays. The script does not measure this judge run.
- `--mode judge` sends each pick and claim to Jev. `--mode no-judge` measures the step overhead with no Jev call.

If you run `benchmark-steps.mjs` without `--e2e`, give `--dir` a copy of `examples/`, for example `/tmp/examples`.
In `judge` and `auto-healing` mode, the script writes lock files next to the specs that pass.

Each area of the product has its own benchmark or eval:

```sh
node scripts/benchmark-planner.mjs --runs 3          # sentence → steps planner vs scripts/planner-cases.json
node scripts/benchmark-picks.mjs --runs 3            # picks with/without goal on saved pages (scripts/pick-states/)
node scripts/benchmark-agent.mjs --runs 3            # a real claude -p agent, changed on vs off (costs Claude usage); --read both: read on vs off
node scripts/benchmark-read.mjs --runs 2 --smart     # read vs smart snapshot on saved pages (scripts/read-states/, read-cases.json)
node scripts/eval-browser-steps.mjs --variant v1     # step-time eval: examples + MCP session, overhead and same step statuses (.claude/hillclimb/, gitignored)
node scripts/benchmark-claims.mjs --runs 3           # expect judging on saved pages (scripts/claim-cases.json); false passes must stay 0
node scripts/benchmark-locators.mjs [--url https://…]   # recorded locators: coverage, and changed pages (wrong hits must stay 0); no key
node scripts/benchmark-steps.mjs --e2e --mode no-judge --runs 3   # step overhead with no Jev call: replays the lock files of a judge run
```

Change the desktop planner only when `benchmark-planner.mjs` shows an improvement. [Performance](performance.mdx)
summarizes the results.

## Documentation changes

If you change step kinds, thresholds, MCP tools, the env file loading or the plugin install steps, change the
matching doc in the same commit. For thresholds and tool names, also change the plugin skill. For the agent
notes, follow `.claude/skills/writing-agent-notes/SKILL.md`.
