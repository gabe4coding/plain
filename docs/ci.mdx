# CI and containers

A CI job for plain needs three things: Node.js, Chromium for browser specs, and a Jev API key
(`TYPESAFE_API_KEY` or `AI_GATEWAY_API_KEY`) as a secret. The job runs the
[`@gabe4coding/plain` npm package](https://www.npmjs.com/package/@gabe4coding/plain) with `npx`. [Getting started](getting-started.mdx) describes the
API key. [Running suites](running.mdx) describes the options, the config file and the exit codes.

## Check specs before a live run

`validate` and `--list` do not need an API key or a browser session. Use them in a pull request job without
secrets:

```sh
npx -y -p @gabe4coding/plain@<version> plain validate tests/
npx -y -p @gabe4coding/plain@<version> plain --list --tag smoke tests/
```

`validate` gives a warning for an absent spec environment variable. `--list` needs these variables.

Write a fixed version in CI, so that a new release does not change your results without a commit. On its first
run, the browser CLI downloads Chromium, also for `validate`. If Chromium of the same Playwright version is
already installed, the CLI uses it.

## GitHub Action

The `action.yml` file at the root of the plain repository runs specs from your checkout. It uses the npm
package at the version of the action ref. Add the API key as a repository secret. A minimal workflow:

```yaml
name: Browser specs
on: [pull_request]
jobs:
  specs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: gabe4coding/plain@main
        with:
          specs: tests/
        env:
          TYPESAFE_API_KEY: ${{ secrets.TYPESAFE_API_KEY }}
```

Pin the action to a release tag, for example `@v3.1.0`, in place of `@main`. Each release gets the tag
`v<version>` after its npm publish. With `@main`, a new release changes your runs without a commit. Also, the
action fails for some minutes after a new version reaches main, until npm has it.

### Inputs

| Input | Required | Default | Meaning |
|---|---|---|---|
| `specs` | Yes | None | Spec files, folders or globs, separated by spaces |
| `args` | No | Empty | More CLI options, for example `--workers 2 --retries 1` |
| `mode` | No | `auto-healing` | [Run mode](running.mdx#run-modes): `judge`, `no-judge` or `auto-healing`. Empty gives no `--mode` option |
| `junit` | No | `plain-results/junit.xml` | Path of the JUnit XML file. Empty disables the JUnit report and its upload |
| `artifacts` | No | `plain-results` | Output folder for screenshots, traces and debug files. Empty disables capture and its upload |
| `artifact-name` | No | `plain-results` | Name of the uploaded artifacts folder. The JUnit file has the name `<artifact-name>-junit` |
| `node-version` | No | `'22'` | Node.js version |

The action parses `specs` and `args` with shell quoting rules, so you can put quotes around a value with spaces.
It does not run them as a shell script.

### What the action does

1. It installs Node.js, the plain npm package at the `version` in the `package.json` of the action ref,
   and Chromium with its system packages.
2. It runs `plain --headless --reporter text`. It adds `--mode <mode>`, `--reporter junit:<junit>` and
   `--artifacts <artifacts>` for each of these inputs that is not empty. Then it adds the `args` and the `specs`.
3. If `junit` is not empty, it uploads the JUnit file with the name `<artifact-name>-junit`. It does this after
   each run, also when the run passes. If the run stops before it writes the file, the upload gives a warning.
4. If the run fails and `artifacts` is not empty, it uploads the `artifacts` folder with the name
   `artifact-name`. With the defaults, the JUnit file is in this folder too.

The action does not publish the JUnit results as a check. To publish them, add a step after the action (see
below).

The action runs in the folder of your checkout. Thus it reads `plain.config.yaml` from there. The action's
`--reporter` options replace the config `reporters`, and `specs` replaces the config `files`. The `mode` input
replaces the config `mode`. To use the config `mode`, set the `mode` input to an empty value. The other
config keys apply.

With the default `mode: auto-healing`, the run replays the committed lock files, and Jev repairs the steps that
changed. The healed lock files stay in the CI working copy. To update the committed lock files, run `plain` on your
computer and commit the files. With `mode: no-judge`, the run makes no Jev call and needs no API key. A `--mode`
option in `args` replaces the `mode` input, because `args` comes after it.

`args` can add a file reporter, for example `--reporter json:plain-results/run.json`. `args` cannot add a
stdout reporter, because the action already uses `text`.

### A full workflow

This workflow publishes the JUnit results as a check:

```yaml
name: Browser specs
on: [pull_request]
permissions:
  contents: read
  checks: write
jobs:
  specs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: gabe4coding/plain@main
        with:
          specs: 'tests/smoke/ tests/checkout/*.yaml'
          args: '--workers 2 --retries 1'
        env:
          TYPESAFE_API_KEY: ${{ secrets.TYPESAFE_API_KEY }}
          # Or: AI_GATEWAY_API_KEY: ${{ secrets.AI_GATEWAY_API_KEY }}
      - name: Publish JUnit results
        if: always()
        uses: mikepenz/action-junit-report@v5
        with:
          report_paths: plain-results/junit.xml
```

The publish step needs the `checks: write` permission. In a matrix, give each job its own `artifact-name`, for
example `plain-results-${{ matrix.site }}`. Artifact names must be unique in a workflow run.

## GitLab CI

This job runs the npm package in your repository, with your specs in `tests/`. It keeps the JUnit report and the
artifacts:

```yaml
browser-specs:
  image: mcr.microsoft.com/playwright:v1.63.0-noble
  variables:
    PLAYWRIGHT_BROWSERS_PATH: /ms-playwright
  script:
    - npx -y -p @gabe4coding/plain@<version> plain --headless --mode no-judge --reporter text --reporter junit:plain-results/junit.xml --artifacts plain-results tests/
  artifacts:
    when: always
    paths:
      - plain-results/
    reports:
      junit: plain-results/junit.xml
```

Set `TYPESAFE_API_KEY` or `AI_GATEWAY_API_KEY` as a masked CI variable.

Use the image tag of the Playwright version that your plain version installs. If the two versions are
different, the CLI downloads its own Chromium on each run.

## Docker

The image uses the Chromium of Playwright 1.63.0 and runs as the user `pwuser`. It installs the plain npm
package at the `version` in `package.json`. Build it from the plain repository, then run it from the folder
that holds your specs:

```sh
docker build -t plain .
docker run --rm -v "$PWD:/work" -e TYPESAFE_API_KEY plain tests/
docker run --rm -v "$PWD:/work" plain validate tests/
```

- The image always adds `--headless`. Give the other options after the image name.
- The mounted folder is the current folder of the CLI. The CLI reads `plain.config.yaml` and `.env` from
  it.
- Set the API key in the host environment and give only its name with `-e`. Do not put the key in a spec or in
  the image. The build does not copy the `.env` file of the repository into the image.
- The run writes reports, artifacts, lock files and `.plain/last-run.json` into the mounted folder. Make
  sure that `pwuser` in the container can write to it.
- Without spec paths, the CLI runs the config `files`. If there is no `files` key, it prints a usage line and
  exits with `2`.
