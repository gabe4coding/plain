# Spec reference

A spec is one YAML file. It has a name, a base URL, optional settings and a list of steps. plain runs
the steps in order.

This page describes browser specs. [Desktop specs](computer-use.mdx#desktop-specs) and
[mobile specs](mobile-use.mdx#mobile-specs) list their differences.

```yaml
name: login works                         # label in the report
url: https://the-internet.herokuapp.com   # base for goto, never opened by itself
goal: log in as the demo user             # optional, every pick sees it
dialogs: accept                           # accept (default) or dismiss
env:
  path: /login
  user: tomsmith
  password: $DEMO_PASSWORD                # read from the environment when the spec loads
tags: [smoke, login]
timeout: 120000                           # time budget for one attempt, in ms
steps:
  - goto: "${env.path}"                   # the first step opens the page
  - fill: { target: the username textbox, value: "${env.user}" }
  - fill: { target: the password textbox, value: "${env.password}" }
  - click: the Login button
  - expect: a heading with the text "Secure Area" is shown
```

Start every spec with a `goto` step. Without it, the first step acts on an empty page and comes back
`inconclusive`. To check a spec without a browser or an API key, run `plain validate <file>`.

## Top-level keys

| Key | Meaning |
|---|---|
| `name` | Required. The label in the report. |
| `url` | Required. The base URL for `goto` steps. plain does not open it. |
| `goal` | One sentence that says what the spec does. Every pick sees it. Claims never see it. |
| `dialogs` | `accept` (default) or `dismiss`. How plain answers `alert`, `confirm` and `prompt`. |
| `auth` | `{ user, pass }`. Credentials for an HTTP Basic or Digest prompt. |
| `geolocation` | `{ lat, lon }`. Sets a GPS position and grants the `geolocation` permission. |
| `env` | Static data for the spec, nested as you like. Steps use it as `${env.*}`. |
| `hooks` | The path of a setup and teardown module, relative to the spec file. See [hooks](hooks.mdx). |
| `tags` | A string or a list, for example `[smoke, checkout]`. `--tag` selects specs by tag. |
| `timeout` | A positive integer in ms. The time budget for one attempt. See [timeouts](#timeouts). |
| `browser` | Browser context settings. See [browser context](#browser-context). |
| `steps` | Required. A list of one or more steps. See [steps](#steps). |

A `goal` helps Jev with a vague target, such as `the comments link`. If the `goal` and the target do not
agree, the target wins.

An unknown key is an error. This applies at the top level, in `auth`, `geolocation` and `browser`, in a step,
and in the keys of a step such as `expect: {that, within}`. Only `env` accepts all keys. The error gives the
name of the key. If a known key is near, the error also gives that key:

```
invalid spec: checkout.yaml: step 2 "expect": unknown key "whithin"; did you mean "within"?
```

Step numbers start at 0. Desktop and mobile specs use the same rule.

### Values from the environment

Do not write credentials in a spec. Put a `$NAME` value in `auth` or `env`, and set the environment variable
`NAME`:

```yaml
auth: { user: $BASIC_USER, pass: $BASIC_PASS }
env:
  account:
    password: $TEST_PASSWORD     # used in steps as ${env.account.password}
```

- plain replaces each string that starts with `$`, at any depth of `auth` and `env`, when the spec loads.
- The full string is the name. `$HOME/x` looks for a variable with the name `HOME/x`.
- An unset or empty variable is an error. `validate` shows it as a warning.
- `validate` also warns about a password or a token that the spec holds as literal text. See
  [check specs without a run](running.mdx#check-specs-without-a-run).
- A `$NAME` inside a list stays as text.

plain also reads [`.env` files](getting-started.mdx).

### Browser context

| Key | Meaning |
|---|---|
| `device` | A Playwright device name, for example `iPhone 15`. Sets the viewport, user agent, touch and scale. |
| `viewport` | `{ width, height }` in pixels, both positive integers. |
| `locale` | The context locale, for example `it-IT`. |
| `timezone` | The context time zone, for example `Europe/Rome`. |
| `colorScheme` | `light` or `dark`. |
| `storageState` | A JSON file of cookies and local storage to load into a new context. |
| `saveState` | A JSON file to write cookies and local storage to, after a passing attempt. |

- A key that you write overrides the same value from `device`.
- `device` does not change the browser. The CLI uses Chromium, unless you set `--channel`.
- The `browser` block rejects unknown keys.

### Stored login state

To log in once and reuse the session in other specs:

1. Write a login spec with `saveState: ./.auth/user.json`.
2. Write the other specs with `storageState: ./.auth/user.json`.
3. Run the login spec first. plain does not order specs by their dependencies.

- Both paths are relative to the spec file.
- plain writes `saveState` only after a passing attempt and its `teardown`. If the save fails, the
  attempt ends `error`.
- If the `storageState` file is missing, the session does not open.

Do not commit state files. They can contain session cookies and tokens.

With [your real browser](agent-mode.mdx#your-real-browser), `--cdp` rejects `auth`, `geolocation` and a
`browser` block that is not empty. `--profile` supports all `browser` keys except `storageState`.

### Timeouts

`--timeout` limits one action and one `wait` step (default `15000` ms). The spec `timeout:`, or
`--spec-timeout`, is the budget for one attempt. The spec value wins, and there is no default budget.

- A retry gets a new budget. Browser launch, `setup` and reporters use part of it.
- When the budget ends, the current step ends `error` with `spec timeout after <ms> ms`. No later step starts,
  also when the step is optional.
- `teardown` and cleanup can continue after the budget ends.

`--timeout 0` disables the action limit. A `wait` that Jev judges then ends at once as `inconclusive`.

## Steps

A step is a mapping with one key, the step kind. It can also have `optional: true`.

An action step names a **target**: a sentence that Jev resolves to one element. A target can also be
`css=<selector>`, which skips Jev. If the selector matches more than one element, the step is
`inconclusive`. If it matches none until `--timeout`, the step is `error`. Use `css=` only as the last choice.

### Actions

| Step | Form | Notes |
|---|---|---|
| `goto` | `goto: /path` or a full URL | Opens the page and waits for the `load` event. |
| `click` | `click: <target>` | Can open a page or a new tab. |
| `dblclick`, `rightclick` | `dblclick: <target>` | Same as `click`. |
| `fill` | `fill: { target, value }` | Replaces the value of the field. `value: ''` clears it. |
| `press` | `press: Enter` | Sends a Playwright key name to the focused element. |
| `hover` | `hover: <target>` | Targets also include images, `svg` and `figure`. |
| `select` | `select: { target, value }` | A native `select` only. Tries the option label, then the option value. |
| `check`, `uncheck` | `check: <target>` | Sets a checkbox, radio, switch or toggle button on or off. |
| `upload` | `upload: { target, files: [a.pdf] }` | Sets the files of an `input[type=file]`, also an invisible one. |
| `scroll` | `scroll: <target>`, `top` or `bottom` | Scrolls a control into view, or the page to its top or bottom. |
| `drag` | `drag: { source, target }` | Drags the source element onto the target element. |
| `mouse` | `mouse: { x, y }` | Moves the mouse to a position in the viewport. `y` can be negative. |

- A `goto` value that does not start with `http://` or `https://` is relative to the full `url`, not to the
  site root. With `url: https://test.example/app`, `goto: /login` opens `https://test.example/app/login`.
- `check` and `uncheck` read the state first and click only if it must change. If the click does not change
  the state, the step is `error`. For a chip or button that shows no state, use `click`.
- `upload` paths are relative to the spec file, also in a [reusable flow](#reusable-flows).
- `fill` supports editable hosts with `contenteditable=""`, `contenteditable="true"` or `contenteditable="plaintext-only"`.
- Natural-language targets exclude `inert` subtrees and native controls disabled by a fieldset, including controls inside shadow roots and frames.
- While a native modal dialog is open, targets come only from that dialog. The page and the frames behind it are excluded.
- A script dialog whose overlay covers the whole page has the same effect. A banner that leaves the page usable, such as a
  cookie bar at the bottom, excludes nothing.
- If `scroll: bottom` reports `did not move`, the content scrolls inside an element. Scroll to an element in
  that area. A heading or a paragraph is not a `scroll` target.
- `drag` moves the mouse in small steps, so native HTML5 drag and drop works.
- For a custom dropdown, click the control, then click the option.

### Checks

| Step | Form | Notes |
|---|---|---|
| `expect` | `expect: <claim>` | Jev judges the claim against the settled page. |
| | `expect: [claim, claim]` | Several claims, one snapshot, one Jev request. |
| | `expect: { that: <claim or list>, within: <target> }` | Jev judges only one region of the page. |
| `wait` | `wait: <claim>` or `wait: { that, within }` | Asks Jev until the claim holds. |
| | `wait: css=<selector>` | Waits until the selector is visible. |

With several claims, one `fail` makes the step `fail`. Else one `inconclusive` claim makes it `inconclusive`.

In a spec or an MCP batch, an `expect` also sends the claims of the next `expect` steps that have no `within`.
If the page is the same when such a step runs, plain uses that answer and sends no new request.

A `within` target names a region, for example `main`, a `dialog`, a `form`, a `table` or a list of results.
Use it on a page that shows more than one thing. It also costs fewer tokens on a large page.

A `wait` looks again when the page changes, or after 1.5 s. If nothing changed since a clear no, it does not
ask Jev again. It stops after 8 Jev answers or at `--timeout`.
A `wait` that never passes ends `inconclusive`, never `fail`. A `wait: css=` that times out ends `error`.

### Reusable flows

Use `include` to share steps, such as a login, across specs. It works on all engines.

```yaml
name: Account settings
url: https://test.example
env:
  user: $TEST_USER
  password: $TEST_PASSWORD
steps:
  - goto: /login
  - include: ./flows/login.yaml
  - click: the Settings link
```

`flows/login.yaml` contains only `steps:`:

```yaml
steps:
  - fill: { target: the Username field, value: "${env.user}" }
  - fill: { target: the Password field, value: "${env.password}" }
  - click: the Login button
```

- plain expands each `include` when the spec loads. A flow can include other flows.
- An `include` path is relative to the file that contains it.
- A flow file with any key other than `steps:` is an error.
- Placeholders in a flow use the `env` and `hooks` data of the root spec. Other paths, such as `upload`
  files, are relative to the root spec.
- Keep flow files out of the folders and globs that you run as specs.

Results name the flow file, for example `flows/login.yaml › click "the Login button"`. The MCP `step` and
`batch` tools do not accept `include`, and `save` does not write it.

### `optional: true`

An optional step that ends `inconclusive` or `error` becomes `skipped`, and the spec continues. Use it for
an element that is not always there, such as a cookie banner.

### How a step waits for the page

Before Jev picks or judges, a step waits until the DOM is quiet and no request is open, for up to 3 s. If the
page needs more time, add a `wait` step.

- The step sends its first look at the page to Jev at once. If the page then changes, plain asks Jev
  again about the settled page. This costs more tokens.
- `click`, `dblclick`, `rightclick`, `press` and `fill` wait for a page that they open to load.
- After `fill`, the next step also waits for a debounced request, such as an autocomplete.
- A new tab becomes the active page. The next step waits until it loads.
- If a step finds no element to choose from, it looks again for up to 2 s.

A run can replay the element that Jev picked in the last passing run. See [run modes](running.mdx#run-modes).

## Step results

| Status | Meaning |
|---|---|
| `pass` | The action or the check passed. |
| `fail` | Jev is sure that an `expect` claim is false. |
| `inconclusive` | No element matches the target well enough, Jev is not sure about a claim, or a `wait` never passes. |
| `error` | An exception, such as a timeout or a navigation failure. |
| `skipped` | An optional step that did not pass. |

The detail of an `inconclusive` step lists the top guesses of Jev and the path of a JSON file with the state
that Jev saw. [Phrasing](phrasing.mdx#how-jev-decides) gives the thresholds.

An attempt stops at the first step that does not pass, except an optional skip.

## What Jev can see

### For a pick

For an action step, Jev gets a numbered list of candidates: the visible, enabled elements that the step kind
can act on. It also gets the page URL and title, the date and the spec `goal`. A candidate description contains:

- the tag, its `type` and `role`, for example `input[type=email]`
- the visible text (max 60 characters) or the field value
- for a form control, the text of its `label` element, for example `label="Cheese"` for a checkbox
- the `aria-label`, `placeholder`, `alt`, `title`, `name` and `id` attributes, and the path of a link
- context from the row, card or group around it, for example the row of an Edit button.

Jev does not get the accessibility tree for a pick. The list puts an open dialog first, then the page, then
`nav` and `footer`, then each iframe with the prefix `[iframe <label>]` (see [iframes](snapshots.mdx#iframes)).
For `click` and `hover`, clickable cards, labels and elements with `tabindex` follow the real controls.
plain also looks inside open shadow roots. A control in a shadow root gets the text of its slotted content.
Identical descriptions get `#1`, `#2` in page order.

Jev classifies each distinct prompt group as semantic or spatial once per browser session.
Some groups need no request:

- An English prompt without a word that can name a position or a size, such as left, below, first, next or larger, is semantic.
- An English prompt with a relation word in lowercase outside quotes, such as left, above or between, is spatial.

A prompt in another language, or a capitalized name such as `the Left field`, goes to Jev.
For a spec or MCP batch, one request classifies all other known groups when the first step needs a model.
If the request exceeds the model limit, smaller requests classify the same groups.
The classification uses resolved targets and claims. Later interactive prompts need another request if their classification is absent.
An uncertain classification requests spatial evidence. A spatial target also gets rendered bounds for candidates and reference elements, such as headings.
These bounds use main viewport CSS pixels and include iframes and open shadow roots. Tree order does not establish visual order.
The reference capture includes at most 254 text elements and controls.
A recorded spatial target replays only while the layout is the same. See [run modes](running.mdx#run-modes).

Over about 1000 candidates, plain drops the last ones (iframes, `nav` and `footer` first). On such a
page, use `within` or `css=`.

### For a claim

For `expect` and `wait`, Jev gets the accessibility snapshot of the settled page, with the tree of each
iframe, and the page URL and title. With `within`, Jev gets only the tree of that region and the page title,
without the URL. plain cuts the snapshot at 60,000 characters, and the step detail then shows
`(aria truncated at 60k chars)`. If the cut removes an open dialog, plain adds the full tree of that
dialog at the end, under `--- open dialog ---`.

A spatial claim also gets rendered bounds for up to 254 text elements and controls.
The layout separates visible text from accessible names. An accessible name does not prove that its text is visible.
A collapsed native dropdown contributes only its displayed selection. Iframe contents require a visible embedding element.
With `within`, these bounds cover only that region.

The observation does not change the page.
If the layout is truncated, scope the claim with `within`. Bounds do not prove color or image appearance.
The browser collects spatial evidence for `expect`, `wait` and MCP `ask`.
Desktop and mobile apps get spatial evidence from their accessibility trees. Read [Desktop apps](computer-use.mdx#spatial-targets-and-claims) and [Mobile use](mobile-use.mdx#what-jev-sees).

A link target longer than 200 characters keeps only its part before `?` or `#`, cut to 200 characters,
followed by `…`. These long targets are usually ad and tracking links. Thus a claim about a long query string
cannot pass. Claim the link text instead. Agent mode gets the same short form (see
[long link targets](snapshots.mdx#long-link-targets)).

Jev also gets the last 30 page events, which the tree does not show:

- dialogs, and how plain answered them
- new tabs
- downloads, with the path of the saved file
- uncaught page errors and `console.error` messages of the page.

Thus Jev can judge `expect: a file was downloaded`. plain deletes the downloads when the browser
closes, after `teardown`. Console errors about blocked resources or from scripts of other sites are not events.

## Placeholders

plain replaces `${env.*}` and `${hooks.*}` in `url` and in every string of every step. It does not
replace them in `goal`, `auth`, `geolocation`, `dialogs` or `browser`.

- `${env.a.b}` reads the `env` block. `${hooks.a.b}` reads what `setup` returned. See [hooks](hooks.mdx).
- The path must name a text, number or boolean value. An object, a list, a missing value, a list index
  (`${env.users.0}`) or another namespace is an error.

plain replaces placeholders after `setup` and before the first step. An unresolved placeholder ends the
attempt `error` before the first step. `teardown` still runs.
